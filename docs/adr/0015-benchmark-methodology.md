# ADR-0015: Benchmark methodology — the rules that make the table defensible

**Status:** accepted · **Date:** day 43 · **Context:** Phase 6's completion
criterion is "the README contains a benchmark table you'd defend in an interview."
Defensible is not a property of the numbers; it is a property of the *method*. This
ADR fixes the method, so the table is reproducible, fair, and honest about where the
tool loses — and so a later day cannot quietly relax a rule to make a number look
better.

## Decision

The benchmark suite (`benchmarks/`, one entry point `python -m benchmarks`) obeys
these rules. Each is a rule because the opposite is a known way to fool a reader.

1. **Fair baselines, with escalating work disclosed.** Overhead is measured against
   `no-instrumentation`, `sys.settrace` no-op, `pdb` with a never-hit breakpoint,
   and `coverage.py` — the tools people actually use — not against a strawman. But
   these tools do *different amounts of work*, and the table says so in a column:
   coverage records a line *set*, ChronoTrace records an ordered event stream and
   (opt-in) every value. **A ratio between unlike work is labelled, never presented
   as a like-for-like win.**

2. **Medians and p95, never best-of-N.** Best-of-N reports the luckiest scheduling
   accident; the median reports what a user gets. Banned, not merely discouraged.

3. **One fresh subprocess per sample.** `sys.monitoring` is process-global and
   sticky; coverage.py and ChronoTrace both `DISABLE` locations and hold tool ids.
   A shared-process matrix contaminates later conditions with earlier de-instrument
   state. Independence is bought by construction, at ~100 ms startup outside the
   timed region.

4. **GC collected then left enabled.** Disabling GC stabilises numbers by flattering
   the allocation-heavy capture condition — the one whose realism matters most — so
   it stays on.

5. **The environment is in the artifact.** Machine, OS, Python, ChronoTrace version,
   git SHA, reps, warmup and GC policy are written into RESULTS.md by the generator.
   A number without its machine is not a number.

6. **Publish the losses, including the observer effect.** Recording overhead is
   large with value capture on; recordings are big; and **recording changes timing,
   so a timing-dependent bug may not reproduce under recording.** All three are in
   the README's "When not to use ChronoTrace," because a benchmark that only shows
   wins is a sales sheet, not evidence.

7. **A number you cannot explain is not published; a number that doesn't exist is
   not fabricated.** 10M-event query latency and 10 GB-recording RSS are not measured
   on the dev machine and are marked as such, not filled with a projection. `--sample`
   does not exist (issue #18); it appears as a planned annotation, never a measured
   row.

## Alternatives rejected

- **Compare only against no-instrumentation.** Flattering and useless: every tracer
  looks terrible against zero. The honest denominator for "should I use this" is the
  tracer the developer already tolerates (pdb), so pdb and coverage are in the table.
- **Best-of-N / GC-off / same-process matrix.** Each makes the numbers *look*
  better or steadier by measuring something other than what a user experiences.
  Rejected as the three classic ways to fool yourself; rules 2–4 forbid them by name.
- **Report a single "overhead" figure.** There is no single figure: overhead tracks
  Python lines executed, so it ranges from ~1× (I/O-bound) to worst-case on a tight
  numeric loop, and flow-only differs from value-capture by orders of magnitude. One
  number would be a lie of omission; the table is per-workload, per-mode.
- **Quietly drop the capture worst case.** The tight-loop + capture cell is the
  number a hostile reader quotes. Hiding it would be the exact dishonesty this ADR
  exists to prevent. It is published, with the escape hatches (scope narrowing,
  planned `--sample`) next to it.

## Consequences

The headline overhead table is regenerated by `python -m benchmarks`, which also
records the environment, so the table cannot drift from the machine that produced
it. Two facts the table makes unavoidable, both healthy:

- **coverage.py is nearly free on hot loops** because on Python 3.14 it `DISABLE`s a
  line after its first execution — it only needs "did this run once." ChronoTrace
  cannot do that for in-scope code: a *trace* needs every execution, a *coverage*
  map needs one. The table shows this rather than hiding behind a scoped comparison.
- **Flow-only worst-case overhead is dominated by per-event `Event` construction**
  (day-4 measured ~827 ns/event). This meets day-4's own stated reversal trigger
  ("switch `emit` to columns if event construction exceeds 10% of recorder time"),
  which is now a live Phase-7 optimisation lever rather than a hypothetical — tracked,
  not fixed today.
